# Браузерный голосовой протокол

WebSocket endpoint: `/api/v1/session`. Клиент передаёт обязательный `Origin`; по умолчанию разрешены `http://localhost:8000` и `http://127.0.0.1:8000`. Другие адреса задаются в `API__ALLOWED_ORIGINS`. Протокол рассчитан на одну активную сессию. Второе подключение получает `session_busy` и закрывается с кодом 1013.

Управляющие сообщения передаются текстовыми JSON-кадрами с `version: 1`. Аудио передаётся отдельными binary-кадрами без WAV-заголовка. Вход — PCM16 little-endian mono 16 кГц, выход — PCM16 little-endian mono 24 кГц. Номинальный входной кадр браузера содержит 20 мс: 320 отсчётов или 640 байт.

## Открытие сессии

Первая команда должна поступить в течение 10 секунд при стандартных настройках:

```json
{
  "version": 1,
  "type": "session.start",
  "language": "ru",
  "input_mode": "ptt",
  "input_sample_rate": 16000,
  "output_sample_rate": 24000,
  "channels": 1,
  "sample_width_bytes": 2
}
```

`input_mode` принимает `ptt` или `auto`; отсутствие поля выбирает `ptt`. Сервер отвечает `session.ready` с `session_id`, `mode`, `input_mode` и подтверждёнными параметрами аудио. Только после этого клиент может начать разговор. Режим ввода не меняется до переподключения.

## Входная речь

В PTT клиент отправляет `input.start`. Сервер возвращает `input.started` с новыми UUID `turn_id` и `generation_id`; затем клиент передаёт binary PCM. После последнего аудиокадра клиент отправляет:

```json
{
  "version": 1,
  "type": "input.commit",
  "turn_id": "11111111-1111-4111-8111-111111111111",
  "generation_id": "22222222-2222-4222-8222-222222222222"
}
```

Нужно использовать идентификаторы из фактического `input.started`; UUID выше служат только примером формата. Commit раньше последнего PCM теряет конец реплики.

В автоматическом режиме клиент непрерывно передаёт PCM после `session.ready`. `input.start` и `input.commit` не отправляются: серверный VAD сам публикует `input.started`, завершает реплику после паузы и выдаёт `response.started`. Новая подтверждённая речь может отменить предыдущий ответ.

Распознавание публикует `transcript.hypothesis` и `transcript.final` с `turn_id`, `generation_id` и `text`. Каждая гипотеза заменяет предыдущую целиком. Пустая финальная транскрипция не запускает LLM.

## Ответ и воспроизведение

| Событие | Поля и смысл |
|---|---|
| `response.started` | `turn_id`, `generation_id`: начата обработка подтверждённой реплики. |
| `response.text` | `generation_id`, `segment_id`, `text`: целая фраза для показа и озвучивания. |
| `response.audio` | `generation_id`, `segment_id`, `sequence`, `byte_length`, `sample_rate`: заголовок непосредственно следующего binary PCM-кадра. |
| `response.segment.end` | `generation_id`, `segment_id`, `total_samples`: весь звук фразы сформирован. |
| `response.done` | `generation_id`: генерация завершена; устройство ещё может воспроизводить полученное аудио. |
| `response.cancelled` | `generation_id`: прежняя генерация остановлена, её звук следует отбросить. |
| `error` | `code`, `message`: безопасная причина отказа команды или реплики. |

Между `response.audio` и соответствующим binary-кадром не допускаются другие события. `sequence` начинается с нуля отдельно для каждой фразы; `byte_length` должен точно совпадать с размером PCM. `total_samples` соответствует сумме полученных отсчётов фразы.

Клиент подтверждает фактически воспроизведённые устройством отсчёты:

```json
{
  "version": 1,
  "type": "playback.progress",
  "generation_id": "22222222-2222-4222-8222-222222222222",
  "segment_id": "33333333-3333-4333-8333-333333333333",
  "played_samples": 24000
}
```

Счётчик монотонный и накопительный для одной фразы; он не превышает число реально отправленных сервером отсчётов. Запись в AudioWorklet ещё не доказывает, что звук услышан: браузер учитывает часы вывода устройства. Полностью подтверждённые фразы могут попасть в историю следующего ответа.

Для ручной отмены передаётся `response.cancel` с текущим `generation_id`. Браузер немедленно очищает воспроизведение, а поздние сообщения отменённой генерации игнорирует. Если заголовок уже принят, соответствующий binary-кадр всё равно нужно потребить перед чтением следующего сообщения.

## Ограничения и диагностика

Стандартные ограничения: 16 КиБ на JSON-команду, не более 100 мс на входной PCM-кадр, 30 секунд на одну реплику, 2 секунды неподтверждённого выходного аудио. Некорректные идентификаторы, формат, порядок сообщений и счётчики отклоняются. Схемы команд и событий находятся в [`session_schemas.py`](../sources/api/schemas/session_schemas.py), пределы — в [`settings.py`](../sources/settings.py).

Браузер пишет в консоль фиксированные диагностические коды `[vox:…]` для проблем разрешений, соединения, протокола и аудиоустройства. Подробности обычных этапов подключения доступны на уровне Debug. Тексты разговора, аудио и содержимое исключений в эти сообщения не попадают.

## Проверка браузерного клиента

Модульные проверки аудиоядра, измерителя и анализатора выполняются без моделей:

```bash
node --test static/test/audio-core.test.mjs static/test/latency.test.mjs static/test/analyze-acceptance.test.mjs
```

Для ручной проверки запустите каскад и откройте [клиент](http://127.0.0.1:8000/). Проверьте разрешение и отказ доступа к микрофону, запись кнопкой и пробелом, завершение реплики после отпускания, остановку ответа и отключение устройства. После переподключения включите автоматический режим: пауза должна завершать реплику, новая речь — останавливать прежний ответ. Используйте гарнитуру и отдельно прослушайте результат: проверки протокола не подтверждают качество распознавания и голоса.
